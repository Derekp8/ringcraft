# Known limitations and deferred work

## External QA gate

The original rules tables and adjudications have not received the requested independent second-human transcription comparison and signed review. Manual page images and the audited GDD were checked during implementation, and deterministic regressions lock the encoded values, but those steps do not replace independent review. This is the principal unresolved correctness risk.

## Private persistence boundaries

1. Saves are browser-local (`localStorage`) plus explicit JSON export/import. A remote sync backend (`RemoteBundleStorage`) exists behind an explicit, configurable endpoint with compare-and-set conflict detection, but no server is configured by default and sync is opt-in — there is no account, server database, cross-device merge, or background backup out of the box.
2. Browser quota, physical save location, private-mode behavior, profile cleanup, and eviction policy are browser specific. Exported campaign JSON is the durable handoff/backup format.
3. Named save files are browser-local (each with timestamps, previews, and duplicate/rename/delete/update-in-place) plus a versioned autosave snapshot ring (newest `N` = 5, each timestamped and restorable from the dashboard's Autosave history). A single-bundle **Export save bundle** / **Import save bundle** round-trips all named saves into one portable JSON document (schema `asw91-campaign-save-bundle-v1`); import merges by campaign identity (never duplicating a campaign, newest `updatedAt` wins in place, ties keep the existing save). A third backend (`RemoteBundleStorage`) syncs the same bundle to a server endpoint with deterministic conflict detection (push/pull/conflict/force), documented in `docs/save-schema-and-migration.md`. There is still no quota management, account, or general save-file manager beyond these backends and the JSON export.
4. The migration registry has only the initial `asw91-campaign-v1` identity entry because no earlier campaign schema exists. Future schema work must add explicit fixtures and notices.
5. Canonical FNV-1a 64-bit hashes establish deterministic identity and replay, not cryptographic authenticity. Package/file checksums use SHA-256.

## Candidate UI boundaries

1. Career exposes automatic match awards and direct attribute spending. The retained Progression Lab remains the broader control surface for skills, maneuvers, and drawback reductions; its manual award form is retained strictly for QA and is rejected by the campaign transaction boundary.
2. The chronological campaign log has free-text filtering and retains the complete saved event history, while the dashboard renders the latest 30 matching entries.
3. Vacancy tournaments require both semifinals to finish before **Advance vacancy bracket** can schedule the final. An early attempt is rejected with a corrective core message and consumes no dice.
4. Public scouting shows current record facts only. There is no hidden plan, future random result, seed preview, or multi-ply opponent analysis.
5. Visual QA is automated Chromium coverage, not a final assistive-technology or human usability certification.

## Rules and content boundaries

1. Matches remain exactly singles or two-person tag. Three-plus-wrestler matches, battle royals, iron-man/last-person-standing rules, managers, weapons, promos, commentary, relationships, booking grades, and GM mode are out of scope.
2. Campaign injuries arise from source-authorized Critical Hold 99/100 results (and Critical Strike 100). An opt-in post-match D20 injury check (`d20-check` campaign option, table `classic-1991-post-match-injury-v1`) adds between-match layoffs for beaten-down or knocked-out participants; it is an adjudicated extension (M10-ADJ-01/02), not a source transcription, and is off by default. Old Injury remains a match drawback.
3. The AI is a deterministic, legality-constrained visible-state policy (`asw91-ai-policy-v1`) with a four-step difficulty ladder: `novice` (v1 greedy plus seeded mistake injection), `standard` (v1 greedy, byte-identical to the pre-M10 policy), `veteran` (1-ply lookahead over a pure positional evaluation), and `ruthless` (2-ply that models the opponent's response) — all within a fixed node budget. Difficulty is a visible configuration stored per match and never a hidden modifier; it changes only which legal action the AI picks, never the rules dice or outcomes. The ladder separation gate samples **32 seeds per window** across the full 0–2300 span (24 step-100 offsets, M10-ADJ-06 — the strict ordering is asserted at every window) with the wide-margin floors kept at the six historical offsets (M10-ADJ-05 trim from 40 — every margin re-measured at the trimmed size, the default policy byte-identical). The wider ordering pin pushes the separation test to ~175 s in the m10 suite, so the full `npm run check` no longer meets the spec's 90-second acceptance target — the cost is recorded in M10-ADJ-06 (a seed trim for the extended windows is a possible follow-up).
4. Cage and ladder matches are a documented digital-only extension (M11-ADJ-01/02/03) revisiting GDD 18.2: the source has no rules for them, so they reuse the manual's dice conventions. Both are singles-only, never end by countout or disqualification (the referee still warns), and add an escape/retrieval D20 win condition; in a cage a Throw Out converts to a cage slam, while in a ladder the floor stays reachable but uncounted. Titles do not change hands on escape/retrieval. The optional `variety` configuration is absent (and byte-identical) for standard matches, and the cage/ladder win-condition formulas are deterministic behavioral assertions, not balance claims.
5. The twelve-month runs demonstrate correctness, reachability, replay, and persistence. Balance and pacing evidence comes from the **M11 seeded playtest balance report** (`fixtures/m11/playtest-balance-report-v1.json`, schema `asw91-playtest-balance-report-v1`): 336 deterministic seeded matches across standard singles, standard tag, cage, and ladder, with pinned win-share-by-difficulty, match-length, and finish-method analytics that the fixture verifier re-derives exactly. The report also caught and fixed a pacing defect in the initial M11 escape formula (see M11-ADJ-02). It is seeded AI-vs-AI evidence; human playtest sign-off remains the external human gate.
6. Contracts and finances, popularity movement, and chemistry pairs are a documented digital-only extension (M12-ADJ-01/02/03): the source defines no such subsystem. Per-wrestler contracts (guaranteed weekly salary, term, optional signing bonus) pay on a fixed 7-day cadence; popularity starts flat at 50 and moves deterministically by official match results (0–100, clamped); chemistry pairs boost tag-win popularity only and never touch the match engine. The optional `financePolicy` field is absent (and byte-identical) when the extension is off. Contracts are not auto-renewed in v1 (renewing means signing again), and popularity is currently a tracked/moving stat with no mechanical effect on booking or match play beyond the tag-win bonus. M12-ADJ-04 and M12-ADJ-05 (adjudicated amendments) then made the tracked stat mechanically matter: title-shot candidates must meet a 40 popularity floor with a graded crowd-heat roll term, bookings prefer the most popular available opponent, and chemistry-pair tag teams gain a flat +2 monthly tag-rating bonus. M12-ADJ-06/07/08 (adjudicated amendments) then added deterministic contract negotiation (`negotiationPolicy: "offers"`, which requires the finance extension): `offerContract` offers a wrestler a contract and resolves their response from a popularity salary curve (fair ≥ 100% of expectation auto-accepts, low < 60% auto-rejects, short offers roll a recorded D20), and at expiry a wrestler is offered a renewal at the expiring salary so one who outgrew their deal may walk. With the opt-in `renewalStrategy: "curve-fair"` amendment (M12-ADJ-09), the campaign AI instead preemptively matches the salary-curve expectation whenever the expiring rate graded below fair, so hot wrestlers re-sign at the curve with a dice-free fair offer; the strategy field is absent (and byte-identical) when unset or "expiring-salary". The optional `negotiationPolicy` field is absent (and byte-identical) when the extension is off; short offers are the only negotiation dice (seeded and recorded), so the ledger stays deterministic.
7. Feuds, feud heat, and month-end booking suggestions are a documented digital-only extension (M13-ADJ-01/02/03): the source defines feuds only as storyline flavor prose. Roster-level feud pairs carry a deterministic 0-100 heat track moved only by the official results of their own matches (no dice); month-end finalization decays cold feuds and emits an advisory booking card for the player (required defense → hottest active feud rival → most popular/highest-ranked available opponent). The feud title-shot term weights already-eligible candidates' rolls and never bypasses the ranking start or the M12 popularity floor. A feud must pair two entrants of the same kind — mixed wrestler-vs-team feuds are rejected at creation and by validation (M13-ADJ-04), since a mixed feud has no division-consistent rival to book. The optional `bookingPolicy` field is absent (and byte-identical) when the extension is off. Suggestions are advisory state only — nothing is auto-scheduled in v1. The feud-and-booking dashboard panel (career setup checkbox, rivalry/heat/booking-card view, and the Start-a-feud control with the singles/tag rival-type toggle) is the M13 campaign UI wiring.

## Implemented M6/private polish

M6 presentation work is implemented without changing campaign rules, schema, data hash, PRNG use, event sourcing, or replay behavior. Automated QA covers onboarding semantics, keyboard dismissal, focus containment, labeled controls, responsive layouts, month-end/post-match panels, dossier exports, and blocked-action guidance. This is still automated candidate coverage rather than a final human assistive-technology certification.

## Implemented M7/playtest readiness

M7 adds structured local notes, deterministic playtest report JSON, and validated shortcuts for the existing M5 completed and in-progress fixtures. Notes are bound to a campaign ID and remain outside campaign state, serialization, hashes, events, and telemetry. The report is diagnostic; campaign JSON remains the exact reproduction artifact.

## Implemented M8/accessibility hardening

M8 adds native Playwright checks for accessible names, landmarks, headings, keyboard traversal, visible focus, dialog focus behavior, live regions, and text-based statuses across all application surfaces. The accompanying checklist explicitly leaves screen-reader, zoom, forced-colors, and human keyboard-only review as external work.

## Implemented M9/private handoff

M9 provides an allowlisted deterministic archive builder and clean-room verifier. The canonical Linux Chromium run remains an external environment requirement when verification is performed on Windows with the Edge fallback. Archive evidence does not change campaign state or compatibility.

## Deferred work after M9

Human assistive-technology review, independent source transcription/adjudication, private content production, and localization remain deferred. Playtest-led balance/pacing evidence is now provided by the M11 seeded playtest balance report (see above); human playtest sign-off on the report's findings remains an external human gate. Audio, installers, platform certification, public branding, marketing, storefronts, telemetry services, rights-clearance work, and commercial distribution are outside this private milestone.
